# 图片字符验证码（静态图 / GIF 动图 / 迷雾 / 停留最长）

## 何时用

仅当页面验证码要求**「读出图里的字符」**时——**不论这张图是静态图还是 GIF 动图**：

本轮唯一动作：`{"solve_captcha": {}}`

（别名 `solve_animated_captcha` 同路径；失败后勿换别名顶次数。）

**不需要自己判断是不是 GIF**：两者同属 `image_text_read` 策略族，分流依据是**图字节事实**（GIF 魔数），不是题面文案。滑块 / 算式 / 点选各自另有策略族，由 `solve_captcha` 自动分发。

## 工具行为

1. 类型门禁：`image_text_read` 之外的策略一律拒绝（滑块/算式/点选不得走本路径）。取到验证码媒体后按**字节**分流，并在回执的 `strategy` 字段如实上报**子模式**：
   - `gif_animated_dwell` —— 图是 GIF（动图）
   - `static_image_read` —— 图是静态图

   `strategy` 是**子模式**，不是策略族 id；族 id 恒为 `image_text_read`。这样日志能区分「静态图读错」和「动图读错」，不会把静态图记成动图而污染排查依据。
2. **GIF 动图**：拉取 GIF → **解析 GIF 逐帧显示时长并换算成每帧相对权重**（`gif_meta.ts`）→ **先定抽样**，再用**一次 GDI 进程**按需拆帧并直接产出 JPEG（原分辨率）；每帧再生成 OpenCV 去噪变体，一起入读码池
   - **抽样早于抽帧**：抽帧是固定开销约 870 ms 的独立进程（单帧真正的编解码只有约 13 ms），抽全部再丢弃等于把最贵的部分白付一遍。帧数取自纯内存解析的 GIF 元数据；元数据不可用（畸形 GIF）时先全量导出、再补一次均匀抽样
   - 帧图以**源帧下标**命名（`frame_<src>.jpg`），即使请求的下标越界被跳过，也不会让「文件 ↔ 源帧」错位
   - 转成 JPEG 是**必须**的：读码请求的 data URL 硬编码 `image/jpeg`，字节若是 PNG，上游解码失败会回**空内容**（这才是历史上「小图读不出」的真正成因，与尺寸无关）；同时必须把 GIF 帧的透明区压成白底，否则透明区转 JPEG 会变黑、读码必废
3. **静态图**：同一张图生成多个预处理变体（原图 + OpenCV 去噪等），每个变体都是一次独立读数。静态图没有「源帧」概念，因此所有变体记作**同一源帧**——它们天然构成「原图 ↔ 去噪图」的配对佐证，正好喂给下面的共识机。
4. **不做固定放大**：放大只是像素复制、不增加信息，上游按 `detail:"high"` 还会自行缩放到同一尺寸。实测原分辨率反而**更保真**：亮度误差 2.28 对 ×4 的 7.33（×4 的最近邻方块被 8×8 DCT 横跨压缩，反引入块效应），色度两者持平（均为 8.5 左右，是 JPEG 4:2:0 的固有代价）；而 ×4 的 data 体积约 ×10
   - 只有**连续读不出**时才对该帧放大重读一次（`upscaleJpeg`）——放大是兜底，不是预置步骤
   - 已是真实 JPEG 的输入（如 OpenCV 变体）直接透传，不重新编解码
5. **时长权重只是「相对重要度」，不是「这帧是答案」的断言**。题面写「停留时间最长」时它是强信号（实测样本 6 帧 `100/100/300/100/100/100ms`，权重 `0.75×5 / 2.25`），但每个验证码结构都不同：有的全部等长、有的带编码抖动。因此
   - 权重 = `delay_i / Σdelay × 帧数`，**无任何绝对阈值**；等长时每帧恰好 = 1
   - 等长 / 无时长信息时，裁决**退化为纯票数**，行为与不启用该功能完全一致
   - 编码器抖动（`100` vs `105`）只产生 ~5% 权重差，自抑，不足以翻转裁决
   - 抽样时优先保留高权帧，避免帧数超限时把关键帧抽掉
6. **并发 4 读码 → 入内存 → 共识裁决**：位数不定；每帧结束后销毁该帧 JPEG/PNG 并释放池槽
7. 裁决按**加权票数**计票，`weightSum` 是第一优先级；其后依次为佐证等客观键：
   - **加权票数**（Σ成员权重；无时长信号时恒等于票数）
   - **佐证**：同一源帧的两个变体（动图=「原图」与「去噪图」；静态图=任意两个变体）互相印证
     - 逐字符完全一致（含大小写）= 最强
     - 字母全同、**双方都自报逐个确认了全部字符**、仅大小写分歧 = 次级（大小写抖动≠看不清）
     - 字母分歧（`UaRU`/`UoRU`、`hgas`/`hga5`）**一律不算证据**：那是真正的识别分歧
   - 排序：加权票数 → 逐字符佐证 → 次级佐证 → 自证全部字符的读数条数 → 独立源帧数 → 读数条数 → 长度等于众数长度 → 可辨字符占比
   - 自我评估分只在上述全部平手时做最后兜底；此时回执标 `weak_evidence`
8. **不做弃权**：永远提交证据最强的候选一次。原设计的「证据不足→弃权→换新码重试」已删除，理由是实测该页点「刷新」后图不变（`unchanged_after_click`），弃权等于 0% 成功率，连续两次运行里弃权都被兜底分支覆盖——净信息产出为 0
9. **提交**：按「显式提交控件 → 文案匹配的提交控件 → 输入框回车（表单提交）」三级降级。**「验证码」是名词不是提交动作**，验证码图/标签绝不会被当成提交按钮（误点会刷新验证码并清空输入框）

## 失败与重试

- 答错后，工具会**点「刷新/换一张」并校验图确实变了**（指纹比对）
  - 换码成功 → 直接再调 `solve_captcha` 解新码
  - 换码失败（`unchanged_after_click` / `no_refresh_control`）→ 本页验证码不会因点击而更换，**不要空转重调**；已验证的提交策略是「把证据最强的候选提交一次」
- **禁止重复填交同一答案**：同一张验证码图 + 同一个答案 = 必然同一个结果，工具会直接拒绝重复提交并换新码
- 工具回执若写明「已填入并提交」，**只做只读核查**（截图 / 读文本 / 看响应），禁止再次 `input` 同一答案
- `captcha_attempt` 由代码计数（不是提示词文案），满 3 次必须 HITL

## 禁止

- 对滑块/算式/点选题死磕本策略（应继续用 `solve_captcha` 自动分发）
- 失败后换别名空转同一路径
- 在「换码失败」或「已提交但无信号」的提示下反复重调 / 重复填交
- 若页面题面要求「使用协议通过验证码」，说明本页校验可能不走页面按钮——此时应按页面要求走接口，不要靠反复提交猜答案
